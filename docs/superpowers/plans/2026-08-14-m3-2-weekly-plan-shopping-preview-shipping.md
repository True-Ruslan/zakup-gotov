## Delivered scope

M3.2 exposes accepted M3.1 WeeklyPlan composition through one stateless contract-first application/API boundary:

`explicit ordered weekly occurrences → server-owned transient identities → accepted WeeklyPlan → accepted M3.1 composition → self-contained WeeklyPlan + canonical ShoppingList + occurrence-aware Recipe provenance`

Delivered production behavior:

- `POST /api/v1/weekly-plan-shopping-previews` returns a transient calculation and persists nothing;
- request owns no UUID/server identities;
- ordered occurrence count is constrained to `1..35`;
- each occurrence owns required `MONDAY..SUNDAY` day metadata, target servings and explicit Recipe input;
- no fixed breakfast/lunch/dinner/snack vocabulary is introduced;
- nested Recipe validation and normalization delegate to accepted `RecipeShoppingPreviewRequestFactory` instead of copying M2.2 title/servings/ingredient/quantity rules;
- transient WeeklyPlan and occurrence IDs are generated by the M3.2 boundary; Recipe/ingredient IDs are generated through accepted M2.2 construction;
- accepted M3.1 `WeeklyPlanShoppingListComposer` remains authoritative for weekly list identity, scaling, canonicalization, merge, exact quantity sum, output order and ShoppingItem identity;
- public provenance exposes only `occurrenceId + recipeId + recipeIngredientId` and every source must resolve inside the returned plan;
- internal `RecipeAggregationEntryId` never appears in response/OpenAPI/generated client;
- malformed JSON, unknown fields/day/unit and non-integer serving JSON return sanitized `INVALID_WEEKLY_PLAN_SHOPPING_PREVIEW` problem details with `$request: malformed JSON request`;
- OpenAPI 3.1 source, pinned `openapi-typescript` output, typed path constant and generated client are synchronized;
- architecture guards prevent M3.2 from reaching provider/retailer/matching/basket/comparison/database layers and prevent accepted lower layers from depending back on M3.2;
- no persistence/history, locality/comparison orchestration, Weekly Planning UI, pantry, nutrition, calendar/time-zone, fuzzy/AI or retailer-network behavior was added.

## Architecture / security / network scope

M3.2 adds no authentication/authorization surface beyond the existing public stateless preview style, no persistence, no sensitive address/locality input and no provider/retailer acquisition path.

The application package depends only on accepted Recipe/Recipe-preview/Shopping/WeeklyPlan semantics plus framework/JDK types. Ordinary CI remains retailer-network-free; existing explicitly gated live probes remain skipped under normal verification.
