# Project State

Updated: 2026-08-09

## Project

**Zakup Gotov** is a recipe-to-cart grocery comparison product. The target experience is: choose what to cook or buy, provide a location, and compare complete grocery baskets across supported nearby retailers using current price and availability data.

Repository: `True-Ruslan/zakup-gotov`
Visibility: Public
Current phase: **M0 — Product & Integration Discovery**
Current execution stage: **M0A — Platform Foundation**
Current task: **Task 5 — Responsive Next.js web shell**

## Product status

The project now has the first user-visible web surface, but it intentionally does **not** pretend that retailer comparison is available. The responsive page explains the product promise and clearly states that retailer integrations and price freshness are still being validated.

No shopping list, recipe, retailer comparison, authentication, matching, or checkout behavior is implemented yet.

## Task 5 TDD and generation evidence

- The Next.js application scaffold was generated by official `create-next-app@16.2.0` in a temporary branch-constrained workflow; that write-capable workflow was removed after the generated files and lockfile were committed.
- pnpm 11 initially rejected dependency build scripts for `sharp` and `unrs-resolver`. Instead of disabling the supply-chain policy, the root workspace now explicitly allows only those two required build dependencies through `allowBuilds`.
- The generated nested `apps/web/pnpm-workspace.yaml` was removed after it caused an ambiguous Next.js workspace-root warning; the repository has one authoritative root pnpm workspace.
- Web test dependencies were added through a temporary branch-constrained workflow and the workflow was removed immediately after its bot commit.
- **Valid RED:** Web CI run `31308735407`, job `93233121289` passed frozen install, shared-client build, ESLint, and TypeScript, then Vitest failed because the untouched generated Next.js page did not contain the required accessible H1 `Закуп готов`.
- Production `page.tsx` was changed only after that RED. The resulting shell contains exactly one H1, honest M0 status copy, and one documentation link; it has no fake store cards, prices, or working comparison CTA.
- The generic generated webfont dependency was removed from the layout. The shell uses a reliable Cyrillic-capable system UI font stack until an explicit design-system typography decision is made.
- The component test was simplified after the page stopped using `next/image`, removing the earlier unused-variable lint warning rather than accepting warning noise.
- **GREEN:** Web CI run `31308894655`, job `93233514803` passed frozen pnpm supply-chain verification, API-client build, ESLint without project warnings, TypeScript, `1/1` Vitest test, and Next.js 16.2 production build.
- **Responsive E2E GREEN:** same run, job `93233572659`, executed Playwright against `next start` in both 1440×900 desktop and 390×844 mobile Chromium profiles. `4/4` tests passed: no horizontal overflow and visible keyboard focus on the documentation link in both profiles.
- Next.js build cache is now persisted with `actions/cache@v5`; the E2E job already restored the cache created by the verify job. `NEXT_TELEMETRY_DISABLED=1` keeps CI deterministic and quiet.

## Current critical unknowns

1. Which Russian retailers expose a technically stable and legally acceptable path to location-specific catalog, price, and availability data?
2. Can at least two providers be supported with sufficient freshness and reliability for a useful basket comparison?
3. What address/location precision must be retained versus used transiently?
4. How should delivery fees/minimum order constraints be obtained and normalized per retailer?
5. What baseline matching accuracy is achievable with deterministic normalization/ranking before AI-assisted matching is justified?
