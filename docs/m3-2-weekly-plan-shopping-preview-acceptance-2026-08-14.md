## Accepted behavior

- stateless preview; no WeeklyPlan/Recipe persistence;
- ordered `1..35` occurrences with `MONDAY..SUNDAY` metadata and no fixed meal-slot vocabulary;
- request contains no client UUID/server identities;
- WeeklyPlan/occurrence IDs are generated by M3.2, Recipe/ingredient identities through accepted M2.2 construction;
- nested Recipe validation/normalization and positive serving semantics delegate to accepted M2.2 request construction;
- accepted M3.1 remains authoritative for weekly ShoppingList identity, serving scaling, unit canonicalization, exact merge, quantity sum, output order and ShoppingItem identity;
- public sources expose exactly `occurrenceId + recipeId + recipeIngredientId` and resolve entirely inside the same response;
- internal `RecipeAggregationEntryId` never leaks;
- malformed JSON, unknown fields/day/unit and fractional serving JSON fail closed with sanitized `INVALID_WEEKLY_PLAN_SHOPPING_PREVIEW` problems;
- OpenAPI 3.1, generated TypeScript schema and typed path constant are synchronized;
- architecture guard prohibits comparison/provider/retailer/database coupling and reverse dependencies into accepted lower layers;
- no locality/comparison orchestration, UI, pantry, nutrition, calendar/time-zone, fuzzy/AI or retailer-network behavior was introduced.
