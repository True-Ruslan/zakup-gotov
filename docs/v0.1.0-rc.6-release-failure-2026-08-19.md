## Reproduction and exact root cause

Recovery PR #180 replayed the rc.6 guard sequence against that immutable staging index on a fresh GitHub-hosted Ubuntu runner using the same pinned GHCR login, QEMU and Buildx setup as release publication.

Failing-before evidence:

```text
workflow run: 32288575493
job:          96183853263
```

The amd64 invocation passed completely. The immediately following arm64 invocation failed during `docker pull --platform linux/arm64` with:

```text
cannot overwrite digest sha256:715c4484cabfcac849bf3d2b9bbbede380f705fb9b666fef67287021a764b460
```

The guard had been pulling the same multi-platform **parent OCI index digest** twice, once per requested platform. Docker's local image store had already materialized the parent reference as the amd64 child and could not overwrite that same digest-pinned reference with the arm64 child.

This was a release-tooling defect, not an arm64 security violation and not an x64-only Sharp matcher defect.

## Recovery design for rc.7

Registry-mode runtime inspection now remains content-addressed while avoiding the local parent-index collision:

1. require the registry input to be pinned by a `sha256` parent index digest;
2. inspect that immutable index with `docker buildx imagetools inspect --raw`;
3. resolve exactly one descriptor for the requested `OS/ARCH[/VARIANT]`;
4. reject missing, ambiguous or malformed platform descriptors/digests;
5. derive an immutable `repository@child-manifest-digest` reference;
6. pull/create the platform-specific child rather than the parent index reference;
7. verify Docker reports the expected `OS/Architecture` before inspecting runtime config and ELF dependencies;
8. retain all existing QUIC and `libssl`/`libcrypto` fail-closed checks.

Local-image mode used by ordinary Container Security CI remains separate and does not require registry index resolution.

The OpenVEX statement, Trivy severities and `exit-code=1` policy are unchanged.
